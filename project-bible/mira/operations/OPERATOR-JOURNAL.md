# МИРА — приватный журнал стадий и canonical dashboard

Версия: checkpoint 07, 2026-09-16. Это воспроизводимое представление исследовательских данных и подтверждённых оператором событий, не новая CRM, не отправитель сообщений и не система выдачи доступа.

## Два разных слоя

Публичные исходники в `data/` и `sales/` описывают найденные компании, проекты и источники. Их пересборка не может назначать подписанный договор, принятого клиента, комиссию или разрешение на контакт. Полный перечень продуктовых функций, исследовательские счётчики и открытые условия находятся в одном месте: `operations/LAUNCH-DASHBOARD.md`, `launch-dashboard.json`, `launch-dashboard.html`.

Операторские события находятся в отдельном **приватном** файле за пределами репозитория. Скрипт читает этот журнал и создаёт отдельное приватное представление того же dashboard. Публичные CSV при этом не изменяются. Пустой пример в репозитории содержит только схему, без настоящих или имитирующих настоящие операции записей.

WEGC — публичный GitHub. Даже opaque-ID и статусы коммерческих отношений могут раскрывать закрытые сведения. Поэтому журнал, его snapshot, результаты приватной сборки и исходные доказательства не коммитятся. В опубликованном коде нет сетевых запросов или автоматической отправки.

## Команды

Публичная пересборка по фактическому состоянию checkout:

```sh
python scripts/mira-launch-build.py --source-commit "$(git rev-parse HEAD)"
```

Приватное представление, когда оператор подготовил реальный журнал в защищённой папке:

```sh
python scripts/mira-launch-build.py \
  --operator-state /secure/mira/operator-journal.json \
  --private-output /secure/mira/render
```

Пути в примере — настраиваемые, а не утверждение о существовании такого хранилища. Оба пути должны быть вне репозитория; исходный журнал не должен находиться внутри каталога результатов. Сам исходный журнал должен быть защищён правами доступа и резервным копированием на стороне владельца. Выходные файлы получают права 0600, новый каталог — 0700. Это не заменяет контроль доступа к устройству, резервным копиям и облачному хранилищу.

## Поля события

| Поле | Значение и проверка |
|---|---|
| `id` | Уникальный opaque `EVT-...`; не имя клиента и не номер договора. |
| `entity_type` | `agency` или `developer`. |
| `entity_id` | Существующий `agency_id` из Launch100 либо `developer_id`, вычисляемый функцией `developer_id(group)` из точного имени группы. |
| `stage` | Только стадия из соответствующей последовательности ниже. |
| `occurred_at` | Фактическое ISO-время с часовым поясом; будущие события не принимаются. |
| `operator_ref` | Opaque `OP-...`; соответствие сотруднику хранится приватно. |
| `evidence_ref` | Opaque `EVID-...`; документ и проверка его актуальности — в отдельном защищённом контуре. |
| `previous_event_id` | Последнее событие этой организации; для первого — JSON `null`. |
| `mode` | `observation`, `transition`, `hold` или `resume`. |
| `next_action` | Код согласованного следующего действия из разрешённого набора. |
| `approval_ref` | Opaque `APR-...`, обязательно для наблюдения внешних действий. Это ссылка на уже существующее подтверждение, не разрешение, создаваемое скриптом. |

Неизвестные поля отклоняются. Контакты покупателей, паспортные данные, банковские реквизиты, суммы, raw URL документов и текст переписки сюда не включаются. Размер входного файла ограничен технической политикой импорта. Документальная подлинность и полномочия оператора не устанавливаются одним форматом ID: этот импорт является операторской аттестацией, а не автоматической юридической проверкой.

Допустимые `next_action`: `confirm_identity`, `confirm_contact`, `request_evidence`, `review_terms`, `prepare_demo`, `approve_outreach`, `wait_owner`, `onboard`, `activate`, `review_registration`, `review_commission`, `follow_up`, `none`.

## Стадии агентства

`qualified → contact_verified → owner_review_ready → owner_approved → contacted → conversation → demo → contract → onboarding → activated → client_registered → active_deal → booking → developer_commission_received → agency_settlement`

| Группа стадий | Основание входа и выхода |
|---|---|
| Квалификация и контакт | Разрешённая идентичность бизнеса, сегмент и релевантный официальный маршрут. Общий email не превращается в подтверждённого руководителя. |
| Owner review / approval | Конкретные адресат, канал, цель, версия текста и объём разрешения. Подготовка черновика не равна approval. |
| Contacted / conversation / demo | Фактическая разрешённая отправка или разговор и отдельно наблюдавшаяся демонстрация. Отправка не подтверждает ответ. |
| Contract / onboarding | Действующие согласованные документы; затем права, ответственный, обучение и допустимый проект. Подпись не доказывает завершённый onboarding. |
| Activated | Содержательное реальное коммерческое действие в разрешённом процессе. Тест, открытие страницы или демо не подходят. |
| Registered / deal / booking | Подтверждённая регистрация у застройщика, отдельно активная сделка и документальная бронь. MIRA receipt не заменяет developer acknowledgement. |
| Commission / settlement | Документированное фактическое получение и отдельный расчёт с агентством. Ожидание, начисление и выплата не смешиваются. |

## Стадии застройщика

`identified → contact_verified → intro → terms_requested → legal_commercial_review → agreement_ready → signed → projects_loaded → inventory_verified → lead_registration_tested → first_agency_activated → first_lead_registered → first_booking`

Вход в commercial review требует конкретных условий и договорного scope. Подпись не открывает все проекты бренда. Загрузка проекта не подтверждает наличие; проверка наличия не заменяет правила регистрации. Внешний тест требует отдельных разрешений владельца и принимающей стороны. Первое агентство, первый лид и первая бронь подтверждаются разными событиями. Название группы, агентский контрагент и продавец покупателю сохраняются раздельно.

## Переходы, исторические наблюдения и паузы

`transition` разрешает следующий последовательный шаг, но не перескок. Для достоверного исторического факта можно записать `observation` на известной стадии: например, обнаруженный договор не заставляет импортировать выдуманную историю звонков, встреч и демо. **Предшествующие стадии при этом не считаются достигнутыми автоматически.**

`hold` сохраняет последнюю стадию и останавливает продвижение; `resume` снимает паузу с той же стадии. Ошибочную или спорную запись нельзя удалять из истории ради улучшения счётчика. Сначала фиксируется hold и выполняется отдельная проверка. Полная модель бухгалтерских сторно или отзывов коммерческих событий здесь не реализована; не использовать этот журнал как замену ей.

События `contacted`, `intro`, `terms_requested`, `lead_registration_tested`, `client_registered`, `first_lead_registered` требуют ссылки `APR-...` при наблюдении/переходе. Скрипт всё равно ничего не отправляет и не выдаёт прав. Наличие этой ссылки в файле не является достаточным основанием для автоматизации внешнего действия.

## Как защищены ручные изменения

`launch-build-manifest.json` сохраняет SHA-256 последнего сгенерированного developer stage register. Перед следующей публичной сборкой содержимое сверяется. При ручном изменении статуса, next action или доказательства сборка прекращается **до** перезаписи файла. Изменения нужно сохранить и осмысленно перенести в приватный журнал, а не удалять manifest, чтобы заглушить проверку.

Для первой миграции проверяются явные признаки операторских стадий и закрытых доказательств. После первого сохранённого manifest защищён весь файл. Исторический исследовательский генератор сохранён как `mira-launch-source.py`; его прямой запуск — внутренний низкоуровневый путь, не штатная команда эксплуатации. Используйте wrapper `mira-launch-build.py`.

Приватная сборка сохраняет snapshot журнала. Следующая версия должна иметь прежние события неизменным префиксом. Удаление, редактирование или перестановка старых событий блокируют импорт. Новый независимый журнал не должен заменять snapshot ради обхода аудита. Этот файловый механизм не является криптографически защищённым удалённым журналом: резервные копии и права владельца остаются обязательными.

## Что означают счётчики

Research coverage — число строк и сопоставлений в текущих источниках. Это не активная агентская сеть и не inventory.

Operator stage observations — число разных организаций, для которых в импортированном журнале явно зафиксирована конкретная стадия. Это **не количество покупателей, сделок, броней или платежей**. Одна организация может иметь много сделок; данный слой не пытается их угадать. При отсутствии полного операционного dataset бизнес-KPI остаются `unknown/null`; конверсии и финансовые суммы не рассчитываются.

Product matrix перечисляет 19 требуемых функций с состоянием исходного кода и хешем файла. Наличие кода и успешные offline-тесты не подтверждают deployment. Статическая публикация Pages, защищённый Worker и коммерческий допуск оцениваются отдельно. Приватный импорт событий не переключает launch-ready и не снимает supply/deployment gates.
